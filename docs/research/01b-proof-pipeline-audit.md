## Three Consequential Corrections

1. **Do not plan to validate a `scarb prove` standalone executable proof via SNIP-36.** SNIP-36 proves virtual Starknet transaction execution under a virtual OS. A physics simulation must either be wrapped as Starknet-contract logic executed in that virtual transaction, or use another proof path.

2. **Do not assume v0.14.4 full-block SNIP-36 capacity is mainnet-live today.** As of **2026-09-25**, v0.14.4’s 1.1B L2 gas support is testnet-live but mainnet is scheduled for **2026-10-05 pending governance**.

3. **Treat the budget model as a hypothesis, not a planning constant.** The public numbers are proof-flow-specific and not enough to justify linear “7 GB/Mstep” or “10 us/step” assumptions. Benchmark your actual Cairo executable/virtual transaction early.

## Important Misses

- SNIP-36 Phase 1 has a **security downgrade** versus native Starknet execution: proofs are verified by Starknet consensus, not yet by SNOS/SHARP/Ethereum settlement. Source: [SNIP-36 security considerations](https://community.starknet.io/t/snip-36-in-protocol-proof-verification/116123).

- SNIP-36 proof data is **not permanently in blocks**; Apollo nodes keep proofs for a finite/TBD period. This matters for auditability and reproducibility.

- For privacy/private inputs, Starknet.js warns that automatic fee estimation can leak calldata to the RPC; manual resource bounds are needed when private input secrecy matters. Source: [Starknet.js SNIP-36 guide](https://starknet-js.com/docs/guides/account/proofs/).
